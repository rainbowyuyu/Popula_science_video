# 创作与协作流程

[返回首页](../README.md) · [文件规范](PROJECT_STRUCTURE.md) · [素材指引](ASSETS.md)

## 从一个可回答的问题开始

每一期先写清：观众是谁、开场看见什么、想解决哪一个问题、结尾能理解什么。避免先列算法和术语清单；用一个生活场景进入，再让画面解释“为什么”。扩充时长应服务理解，不能靠重复讲稿填满时间。

## 一次修改的最小记录

在项目文档中说明：

- 修改目标与时间范围；必须保留的旁白、模型或视觉规范。
- 当前真实入口、依赖和相关来源。
- 本次修改涉及的文件及新输出位置。
- 检查方法、结果、未覆盖范围与回退入口。

新版本独立输出；不要用局部无声预览覆盖正式成片。文件与目录命名见 [工程规范](PROJECT_STRUCTURE.md)。

## 双模型如何合作

模型按具体问题分工，不用“一个只能建模、另一个只能写代码”的硬边界。每次交接包含真实文件、已确认事实、当前问题和验收条件；同一个入口文件由一位实现者负责整合，避免并发写入。

可以让另一模型提出镜头、修复局部组件或审阅科学表述，但必须以运行结果、实际帧、音频和来源复核。两个模型互相赞同不等于验证通过。私有接口设置来自本机环境，提示词与日志中不复制凭据。

## 制作顺序

1. **故事与依据**：形成自然的叙述，建立事实、公式与教学示例来源。
2. **声音与时间**：按实际旁白时长安排镜头，校正多音字、英文缩写与不自然断句。
3. **机制与镜头**：建立可读的模型和运动关系；前后镜头有明确的主体接力。
4. **短样片**：先看代表帧和关键转场，检查比例、阴影、材质、字幕与遮挡。
5. **完整输出**：渲染、混音、字幕对齐与技术 QA。
6. **封面与发布**：按系列固定锚点分别设计四个画幅，文案准确对应片中内容。

## 检查要写到什么程度

| 检查 | 能说明什么 | 不能代替什么 |
|---|---|---|
| 类型检查 / 单元测试 | 对应代码或算法条件通过 | 全片视觉正确 |
| 时间线与帧数检查 | 时长、边界、音画结构符合规则 | 旁白自然、镜头有美感 |
| FFprobe / 解码 | 容器、编码与可解码性 | 每一个画面没有穿模 |
| 代表帧抽查 | 所列时点的排版、材质与主体 | 未检查区间的连续运动 |
| 音频响度 / 峰值 | 音量与峰值范围 | 字音与情绪准确 |
| 人工连续审看 / 复听 | 实际检查区间的观看效果 | 没有查看的其余版本 |

报告写出真正执行过的范围。教学示意、程序点云、固定数据示例与真实实验数据分别标明；未调用的仿真工具不出现在技术路线的已用工具清单中。

## 提交前

确认项目导航与实际文件一致；新增源资产有出处和使用范围；没有凭据、私有录音、依赖目录或渲染缓存。源码变更提供相应验证。大量生成媒体通过资产清单和独立交付方式管理，不塞进 Git 历史。

不要为整理这个仓库改动源工作区其他视频项目，也不要用根目录级清理来代替项目内的依赖判断。
